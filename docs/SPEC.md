# Personal Study App — Product Specification

## 1. Purpose

A self-hosted personal study application for reviewing university subjects using spaced repetition.

The application is designed for a single user and runs on the user's own laptop using Docker.

The application must be usable from:

- desktop browser;
- laptop browser;
- mobile browser on the same network.

Questions and answers are generated externally with ChatGPT and imported into the application as JSON.

The application itself does not generate questions with AI.

---

# 2. Main Study Structure

The content hierarchy is:

```text
Subject
  └── Section
        └── Question
```

Example:

```text
Electronics for Embedded Systems
├── Memory Fundamentals, Organization & Interface
├── SRAM
├── DRAM
├── Flash Memory
└── Memory Interfacing
```

A subject contains multiple sections.

A section contains multiple questions.

---

# 3. Question Types

V1 supports four question types:

```text
recall
concept
problem
code
```

### recall

Short factual recall.

Example:

> What are the three SystemC process types?

### concept

Explanation or comparison.

Example:

> Explain the difference between SRAM and DRAM.

### problem

Engineering/calculation problem.

Example:

> A digital memory is organized as 4K × 9. Determine its total size, address width and valid address range.

### code

Questions requiring understanding or recalling code.

Example:

> Write the basic structure of an SC_THREAD-based synchronous counter.

Question type is metadata only.

All question types use the same self-assessment workflow.

---

# 4. Question Content

Questions and answers may contain:

- Markdown;
- bold and italic text;
- lists;
- inline code;
- fenced code blocks;
- mathematical formulas;
- LaTeX block formulas;
- long explanations.

Example:

```latex
N_{words}=2^{12}=4096
```

Long-form engineering questions are a normal use case.

The UI must not assume every question is a short flashcard.

---

# 5. Review Workflow

The primary study workflow is:

```text
Question
   ↓
Think about answer
   ↓
Show Answer
   ↓
Read reference answer
   ↓
Self-assess
   ↓
Again / Hard / Good / Easy
   ↓
FSRS schedules next review
```

There is no automatic answer grading in V1.

The user does not need to type an answer.

---

# 6. Review Ratings

Every completed review must use one of:

```text
Again
Hard
Good
Easy
```

The selected rating is passed to the FSRS scheduler.

The application must store review history permanently.

---

# 7. Review Mode

Review mode shows questions that are due according to FSRS.

The home page should show at minimum:

```text
Due today
New questions
Reviewed today
```

Starting a review should present due questions one at a time.

Before revealing the answer:

```text
Subject
Section

Question

[Show Answer]
```

After revealing:

```text
Question

Answer

[Again] [Hard] [Good] [Easy]
```

After selecting a rating, the application immediately loads the next question.

---

# 8. Practice Mode

Practice mode is independent from FSRS scheduling.

The user can manually practice questions even if they are not currently due.

The user can select:

- subject;
- section;
- all sections in a subject;
- weak questions;
- random order;
- number of questions.

Example:

```text
Practice

Subject:
Electronics for Embedded Systems

Section:
Memory Fundamentals

Questions:
20

[x] Random order
[x] Include already mastered questions

[Start Practice]
```

Practice mode must not accidentally modify FSRS review scheduling unless explicitly designed to do so.

For V1, practice sessions should be independent from scheduled reviews.

---

# 9. Subjects Page

The application should show subjects such as:

```text
Electronics for Embedded Systems
Computer Architectures
Testing and Certification
Modeling and Optimization of Embedded Systems
SystemC
```

Each subject should show basic information such as:

```text
Total questions
Due questions
Sections
```

Selecting a subject opens its sections.

---

# 10. Section Page

A section page shows:

- section name;
- parent subject;
- number of questions;
- due questions;
- question list.

The user can:

- start practice;
- edit questions;
- delete questions;
- inspect individual questions.

---

# 11. Question Editing

Questions generated by GPT may contain mistakes.

The user must be able to edit:

- question;
- answer;
- type;
- difficulty level;
- tags;
- source;
- source page;
- section.

Changes must persist immediately in PostgreSQL.

---

# 12. JSON Import

Questions are created externally using ChatGPT.

The main content ingestion workflow is:

```text
Lecture material
      ↓
ChatGPT
      ↓
JSON file
      ↓
Study App
      ↓
PostgreSQL
```

The application must allow:

```text
Upload JSON file
```

and preferably also:

```text
Paste JSON
```

The importer must validate the JSON before writing it to the database.

---

# 13. Duplicate Protection

Importing the same JSON twice must not create duplicate questions.

Questions have an `external_id`.

Example:

```text
efes-memories-001
efes-memories-002
efes-memories-003
```

If an imported `external_id` already exists, the question should be considered a duplicate.

The import result should show something similar to:

```text
Received:   50
Imported:   46
Duplicates: 4
Errors:      0
```

---

# 14. Mobile Requirements

Review mode is mobile-first.

The application must work comfortably on screens approximately 360px wide and above.

Requirements:

- large readable text;
- no required hover interactions;
- large touch targets;
- vertically scrollable long answers;
- review buttons easy to press;
- formulas must fit or scroll correctly;
- code blocks must horizontally scroll if necessary.

The full review workflow must work comfortably from a phone.

---

Study Dashboard

---

# 16. Weak Questions

A question may be considered weak when the review history contains repeated:

```text
Again
Hard
```

V1 does not need a sophisticated AI weakness detector.

Simple review-history-based filtering is sufficient.

---

# 17. Persistence

Study data is important and must survive container recreation.

The following must not delete data:

```bash
docker compose down
docker compose up -d
```

and:

```bash
docker compose up -d --build
```

PostgreSQL must use a Docker named volume.

---

# 18. Backups

The project must provide a simple database backup mechanism.

For example:

```bash
./scripts/backup.sh
```

Backups should be written to a local directory such as:

```text
backups/
```

The application should eventually support JSON export of study content.

---

# 19. V1 Non-Goals

Do not implement the following unless explicitly requested:

- multiple users;
- registration;
- cloud hosting;
- social features;
- leaderboards;
- AI question generation;
- automatic GPT grading;
- RabbitMQ;
- Redis;
- Celery;
- microservice architecture;
- native Android/iOS applications;
- complicated gamification.

The goal is a reliable personal engineering study tool, not a commercial learning platform.
